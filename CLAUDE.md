# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Facheiro is a malware scanner and incident-response toolkit for compromised WordPress sites, shipped as a **WordPress plugin** (this repo is the plugin folder, slug `facheiro`) whose scanning engine also runs as a **standalone CLI** with no WordPress. Audience: incident responders. It must run on locked-down shared hosting and degrade gracefully when curl/zip/zlib/mysqli are missing.

Layout:

- `facheiro.php` — plugin main file (headers, constants, requires, hooks). PHP 7.2+.
- `includes/engine/` — the engine, namespace `Facheiro\Engine`, **PHP 5.6 syntax** (no `??`, typed properties, arrow functions, `fn`), **no WordPress functions**, no `$_GET`, no `echo`, no `exit`. Loaded by `includes/engine/load.php`.
- `includes/plugin/` — WordPress side (PHP 7.2+): `Facheiro_Plugin` (bootstrap, table, `make_context()`), `Facheiro_WP_Http` (WordPress HTTP API adapter), `Facheiro_WP_Db` (`$wpdb` adapter), `Facheiro_Job` + `Facheiro_Store_Reporter` (resumable admin scan), `Facheiro_Settings` (runner mode, schedule, log path; option `facheiro_settings`), `Facheiro_Cron` (WP-Cron background runner `facheiro_run_job` and the recurring `facheiro_scheduled_scan`), `Facheiro_False_Positives` (review marks, option `facheiro_false_positives`), `Facheiro_Sample` (encrypted sample zip), `Facheiro_Signatures` (custom signature store, option `facheiro_signatures`, installed into the engine whenever `make_context()` builds a scan Context), `Facheiro_Abilities` (WordPress abilities for AI assistants over MCP), `Facheiro_Hardening` (web server rules: Apache/LiteSpeed `.htaccess` blocks and the Nginx file, apply with health check and rollback, live checks; option `facheiro_hardening`), `Facheiro_Recovery_Key` (the key file that unlocks recovery mode), `Facheiro_Admin` (top-level Facheiro menu with Scan / Signatures / Hardening / Recovery / AI assistants tabs, ajax, settings form, export; the Hardening and Recovery tabs live in `Facheiro_Admin_Hardening` and `Facheiro_Admin_Recovery`), `Facheiro_CLI` (WP-CLI, including `harden` and `recovery-key`).
- `bin/facheiro.php` — standalone CLI entry (`php bin/facheiro.php key=value ...`); refuses non-CLI SAPIs.
- `recovery.php` + `includes/recovery/` — recovery mode: a key-protected web page that runs the engine **without WordPress** (namespace `Facheiro\Recovery`, PHP 5.6 syntax like the engine, its own escaping/CSRF/session code because no WordPress function exists there).
- `tests/` — `regress.sh` (old-vs-new output diff), `chunking.php` (resumability), Playwright `admin-ui.js`, `background-ui.js`, `findings-ui.js`, `signatures-ui.js`, `hardening-ui.js` (needs Apache with `AllowOverride All`), `recovery.js` (breaks and repairs the site), and `mcp-stdio.js` (MCP session through the MCP Adapter). No PHPUnit.

## Commands

```sh
php -l <file>                                # lint — run after every change
php bin/facheiro.php help=1                 # CLI options
tests/regress.sh [old-ref]                   # must report failed=0 (DB cases need the MariaDB fixture; see TESTPLAN E)
php tests/chunking.php /path/to/wp-root      # must print IDENTICAL
php build/make-checksums.php                 # after changing ANY tracked file: rewrites checksums.json
php build/make-zip.php                       # release package dist/facheiro.zip (what Plugin Check and WordPress.org get)
tests/checksums.sh                           # checksums.json current + self-check cases: must report 0 failed
WP_PATH=... WP_CLI="wp" tests/tamper.sh      # sealed settings on a WordPress test site: must report 0 failed
composer install && composer phpcs           # WordPress security/DB/WP sniffs + PHPCompatibilityWP: must be clean
```

Testing is done by building synthetic fixtures (fake WordPress root, tampered files, crafted logs, offline manifests via `checksumdir=`) and asserting on the output; `TESTPLAN.md` is the canonical list, including the live wordpress.org API tests and the plugin tests (section F) that need a real WordPress install. Every scanner needs a positive case and its false-positive negatives.

## Engine contracts

- **Context** (`context.php`) carries the options (same `key=value` names as the CLI: `scandirectory`, `contentdir`, `plugindir`, `dryrun`, `allfiles`, `scanlog`, `correlate`, `window`, `checksumdir`, `locale`, `restore`, `quarantinedir`, `selfcheck`, `noselfcheck`, `format`), the Reporter, the `Http` and `Db` adapters, `plugin_dir` (never scanned), `work_dir`, and an optional `deadline`. Read options with `$ctx->has()/get()`; derive variants with `$ctx->with()`.
- **Reporter** (`reporter.php`) is the only output path: `finding($severity,$type,$path,$detail,$context,$meta)`, `summary($scan,$data,$text)`, `progress($text)`, `fatal($message)`, `exit_code()`. `TextReporter` prints `SEVERITY,TYPE,path,detail` (attacker-controlled fields percent-encoded, context indented) and buffers for scanall's severity-sorted flush; `JsonReporter` prints NDJSON events on stdout and progress to STDERR; the plugin's `Facheiro_Store_Reporter` writes to the findings table. Never `echo` from a scanner. A value that is not valid UTF-8 (a file name, a log line, a database value cut mid-character) is cleaned where the output needs UTF-8 (`BaseReporter::clean_utf8()`: JSON events, the findings table, recovery state) and never dropped; text output prints the raw bytes.
- **Fatal** (usage errors, unreadable targets, non-WordPress root, standalone DB failure) is thrown, never exited; entry layers catch it and present it (text `Error: ...`, JSON `{"event":"error"}`, WP-CLI halt 1, admin job `failed`).
- **Admin job** (`Facheiro_Job`): the attempt record is saved *before* a unit runs and a unit started more than `MAX_ATTEMPTS` times fails the job; a PHP fatal inside a step is recorded through the `wp_php_error_message` filter (WordPress's own fatal handler dies before any later shutdown function). A unit must always make progress (byte offset, primary key, range end) or the attempt counter will stop it. In background mode (`$job['background']`, the default runner) `Facheiro_Cron::run_job()` loops `step($stop)` inside one cron request for a chunk, schedules a safety single event before it starts, and chains the next request from a shutdown function (`spawn_cron()` refuses inside a cron request); the page only polls `facheiro_status`, kicks once when idle for `STALE_SECONDS`, then steps itself. Scheduled scans always run in the background. Every finished job calls `Facheiro_Cron::clear_step()`; deactivation cancels and clears all events.
- **Scanner** (`scanner.php`): `init_state()`, `plan(&$state)` → list of serialisable units, `run($unit, &$state)` → `null` or unit(s) to run next, `finish(&$state)`. Units and state are plain arrays so the admin job can persist them between requests; a scanner checks `$ctx->out_of_time()` and returns a continuation unit (byte offset, primary key, file-list position) instead of blocking. `Scanner::run_all()` is the CLI path; `Runner::make_stage()`/`scanall_stages()` is the stage list shared by `run_scanall()` and `Facheiro_Job`.
- **Layout** (`layout.php`): where plugins, themes, uploads and mu-plugins live. Never hardcode `$root . '/wp-content'`: ask `Layout::of($ctx)` (`content_dirs`, `plugin_dirs`, `outside_root`, `in_content_subdir()`, `has_plugin()`). Sources: the `contentdir=`/`plugindir=` options (`make_context()` fills them from `WP_CONTENT_DIR`/`WP_PLUGIN_DIR` for a scan of the site itself; recovery passes its plugin folder), else the `wp-config.php` defines parsed with a tiny grammar. `<root>/wp-content` is always scanned too when it exists; whole-tree walks go through `scan_roots()` so folders outside the root are reached. Layout findings (`CONTENT_DIR` INFO, `CONTENT_DIR_UNKNOWN` ERROR) are reported once: by the quick scan inside scanall, by each scanner on its own otherwise. A run that may write never follows a `wp-config.php` define out of the root.
- **Folder walks** (`TreeWalk` in `files.php`): every scanner walks folders through it, never through `RecursiveDirectoryIterator`. It follows a symbolic link to a folder (a linked uploads folder must not hide its files) but never to a parent, to the filesystem root, into a folder a walk already covers, or twice, so a planted `x -> /` cannot walk the disk or loop; it lists the folders it could not open in `$unreadable` and, with `$follow` off, the links it left alone in `$refused`. The caller reports both (`Scanner::report_walk()`, `IntegrityScanner::package_files()`). The signature scan passes `$follow = false` when it may write (`Layout::may_write()`), so a cleanup never leaves the folders it was given; integrity and timestamp walks only list files and always follow, and restore keeps its own guard (`is_inside()`). The tool's own folder is never scanned, so a scan directory inside it is refused with a Fatal (`require_outside_tool()`).
- **Adapters**: `Http::get()/download()` (`CurlHttp` standalone, `Facheiro_WP_Http` in WordPress — TLS verification is never disabled anywhere); `Db::connect()/each(query, callback, after)` (`MysqliDb` streams with `MYSQLI_USE_RESULT`, `Facheiro_WP_Db` walks primary-key *ranges* with an adaptive range size and checks the Context deadline between ranges, so one query never scans the whole table and the cursor advances even when nothing matches; both iterate in pk order and the engine's queries are fixed SQL with `ORDER BY pk`). SELECT-only, never `unserialize()`. `Db::prefix()` is the base prefix (never `$wpdb->prefix`, which is a sub-site's under `--url=`), `Db::site_prefix($site_id)` and `Db::table($short, $site_id)` name one site's tables (site 0 is a single site's own; `users`, `usermeta`, `blogs`, `sitemeta` are network-wide and ignore the id; a site id is only ever used as an integer). `Db::multisite()` says whether the install is a network: `DatabaseScanner` then plans a `network` unit (`{base}sitemeta`: `site_admins` parsed by declared string length with `serialized_strings()`, `active_sitewide_plugins`, option signatures), a `superadmins` unit (the users the list names, matched server-side as bytes), the main site's three units, and a `sites` unit that reads `{base}blogs` `SITE_BATCH` ids at a time and returns each site's `admins`/`options`/`posts` units (they carry `'site' => id`) followed by itself for the next batch, so the queue never holds the whole network. On a single site the plan, the units, the finding text and the summary keys are exactly what they were (`SITES`/`SUPER_ADMINS` and `of site N` appear only on a network).
- **Signatures** (`signatures.php`) are static arrays compile-checked by `Signatures::lint()` before every scan; a malformed regex throws Fatal naming the signature. Cleanup signatures have `prefilter` + `triggers` (ALL must match) + one `action` (`remove_regex`/`delete_file`/`report`/`detect`). Built-ins live in `builtin_*()`; `cleanup()` is `builtin_cleanup()` + `builtin_detection()` + the custom set from `set_custom()` (first match wins, so a custom rule can never re-label a built-in HIGH), `db_options()`/`db_posts()` append the custom set. `builtin_detection()` is the report-only generic webshell/backdoor set (`MALWARE_FOUND`, never cleans, even without `dryrun`); a file nothing matched gets a second look at `normalize_code()` output (comments removed, string fragments joined, letter escapes decoded), for that set only. Every detection signature needs a positive fixture in `tests/fixtures/detection/` (stored as `.txt`: a `.php` there would be a live backdoor in a git-cloned plugin) and must stay quiet on WordPress core and popular plugins. Custom signatures come only from definitions (`validate_definition()`, `from_definitions()`, JSON via `parse_file()`, shared by the plugin editor, the abilities and the CLI's `signatures=`) and are **detection-only**: `set_custom()` forces the `report` action (`SIGNATURE_MATCH`), so no operator- or assistant-written regex can ever rewrite or delete a file. Patterns that match the empty string are refused.
- Exit codes: 0 clean/INFO, 1 fatal, 2 LOW/MEDIUM/ERROR, 3 HIGH. Anything that blocks a check (unreadable file or log, missing zlib/zip/mysqli, unreachable DB, failed query, disabled `shell_exec`, failing `crontab -l`) is an `ERROR` finding (`INTEGRITY_UNREADABLE`, `LOG_UNREADABLE`, `DB_UNAVAILABLE`, `DB_QUERY_FAILED` (also a network's list of sites that cannot be read, or a listed site whose tables are missing), `CRONTAB_UNAVAILABLE`, `SYMLINK_NOT_FOLLOWED`, `INTEGRITY_NO_REFERENCE` when a reference could not be fetched or read (it stays INFO when there is no official reference, or none in `checksumdir=`), `FILE_UNREADABLE` for a folder that cannot be listed, and in the signature scan `FILE_UNREADABLE`, `FILE_TOO_LARGE` for PHP and `SIGNATURE_ERROR` when PCRE gives up on a regex) so it shows in the exit code — a silent skip makes "clean" mean "never looked". Note `function_exists('shell_exec')` is true for a `disable_functions` entry; check `ini_get('disable_functions')` too.

## Plugin side rules (WordPress.org guidelines)

- Prefix everything global: `Facheiro_*` classes, `facheiro_*` options/hooks/table, `FACHEIRO_*` constants, text domain `facheiro`. `if (!defined('ABSPATH')) exit;` at the top of every plugin-side file.
- Portuguese (pt-BR) is the source language: every admin string is written in Portuguese and goes through `__()`, `esc_html__()` and friends with the `facheiro` domain (JS strings through `wp_localize_script`, so the PHP side translates them). Changing or adding one means regenerating `languages/facheiro.pot`, updating `languages/facheiro-en_US.po` with its English translation, and recompiling `.mo` and `.l10n.php` (commands in `docs/development.en.md`, Translations); `Facheiro_Plugin::load_textdomain()` shows that English catalogue for every `en*` locale. Text that is saved and shown later (check results, notes) is stored as data and turned into text when displayed, so it follows the reader's language. Recovery-page strings are written in Portuguese, go through `App::t()`/`App::e()` and need an English line in `includes/recovery/i18n/en.php` with identical placeholders (`i18n/pt_BR.php` only translates the engine's stage names). Engine finding details stay English (exports, CLI). `README.md` is Portuguese and `README.en.md` is its English counterpart: change both together. The README is short (overview, install, first steps, links); the user guides live on the GitHub wiki (Portuguese and English pages, a separate repository updated after the merge), the reference (output format, JSON events, exit codes, what each scanner checks) in `site/referencia/index.html` and `site/en/reference/index.html`, and contributor docs in `docs/development.md` / `docs/development.en.md`, which lists where each topic goes.
- Capability `manage_options` plus `is_super_admin()` on multisite (`Facheiro_Plugin::can_manage()`); nonce on every ajax/admin-post action; free-text inputs are bounded and validated before use: the log path must `realpath()` to a readable file/dir, any path read for display or testing must `realpath()` inside `ABSPATH` and never be a `wp-config*` file, false-positive notes go through `sanitize_text_field()` and a length cap, and signature conditions go through the engine's `Signatures::validate_definition()` (regexes must compile and must not match an empty file); escape all output (findings are hostile data); `$wpdb->prepare()` for every value; table name from `$wpdb->base_prefix`.
- The admin page is **report-only** for the site's content: it never cleans, restores, changes site files or the database. Destructive actions are WP-CLI/CLI only (`wp facheiro scan`, `wp facheiro integrity --restore`), with `--dryrun`. The one exception is server configuration on the Hardening tab, under these rules: Facheiro writes only its own `# BEGIN Facheiro` / `# END Facheiro` blocks (`insert_with_markers()`), refuses up front if any needed file is not writable, checks the home page, login and admin-ajax before and after and restores every file byte-for-byte if any of them starts failing, and removal leaves files exactly as they were (files it created are deleted). Nginx configuration is never written: it is downloaded and included by the administrator. The live check (`Facheiro_Hardening::check()`) only sends requests for files that do not exist, so it creates nothing on the site.
- Outbound requests only to `api.wordpress.org`/`downloads.wordpress.org`, only during an integrity check, disclosed in `readme.txt` (External services). No telemetry, no remote signature feeds, no CDN assets; `assets/admin.js` is vanilla, no build step. No site-wide admin notices.
- Direct filesystem writes (atomic temp+rename, quarantine) and `shell_exec('crontab -l')` are deliberate and documented in `readme.txt` FAQ; each site carries a `phpcs:ignore` with the reason. Keep `composer phpcs` clean.
- Plugin Check (what WordPress.org runs) does not read `phpcs.xml.dist`, so the files that also run without WordPress (the engine, `bin/facheiro.php`, the recovery page) carry a `phpcs:disable <sniff> -- reason` at the top for the checks that assume WordPress is loaded (escaping functions, `WP_Filesystem`, `$wpdb`, the HTTP API, nonces). Plugin-side files get no such file-wide switch: there the fix is the WordPress API, or an inline `phpcs:ignore` with its reason. Run Plugin Check on the release build (`php build/make-zip.php`, then install `dist/facheiro.zip`), never on the checkout: rows for `tests/`, `build/`, `.claude`, `CLAUDE.md`, `TESTPLAN.md`, `.distignore` or `phpcs.xml.dist` mean the checkout was checked.
- `readme.txt` `Stable tag` must equal `Version:` in `facheiro.php` and `FACHEIRO_VERSION`; bump all three together. `.distignore` keeps tests/tooling out of the WordPress.org zip.

## Invariants — do not break these

- **Fail closed**: only `preg_match(...) === 1` counts as a match; engine errors (`false`) and unknown condition/action types never flag or clean a file.
- **`dryrun` must cover every destructive action** (writes, deletes, restores). A dry run that touches disk is a P0 bug — this happened once with `DELETE_FILE`. `scanall` forces `dryrun` and drops `restore`.
- **Restore safety**: content is byte-verified against the reference checksum manifest before writing (a tampered package zip must be refused); `INTEGRITY_EXTRA` files are never deleted or overwritten; failed quarantine aborts the overwrite; writes go through `write_cleaned_file` (temp file + rename, never truncate in place). Every write and quarantine copy must stay inside the package or quarantine directory: manifest and zip entries must be plain relative paths (`is_safe_relative_path()`), a target that is a symlink is refused, and the target folder must `realpath()` inside the package (`is_inside()`), because the web user can plant symlinks and the restore may run as a more privileged operator. Version headers are allowlisted (`is_safe_version()`) before they reach a URL or file name.
- **Heuristics are report-only**: timestamp and correlation findings must never feed a cleanup or restore action, and their output says "leads, not proof".
- **Never disable TLS verification** — the tool runs on already-compromised hosts; an "all clean" answer must not be attacker-supplied. Treat API responses and everything read from the scanned host (filenames, log lines, file contents, DB values) as hostile data.
- **Memory/scale**: logs are streamed line-by-line, zips streamed to disk, per-minute bucketing bounds correlation memory, DB values capped at 256KB, file lists go to a work file. Don't buffer unbounded input.
- **The engine never scans itself**: `is_scannable_file()` skips `Context::$plugin_dir` (the signature strings in the source would match). Instead the `self` stage (`SelfCheckScanner`, first in `scanall_stages()`, also before `scanintegrity`) verifies the plugin's files against the wordpress.org checksums, else the shipped `checksums.json`; the integrity stage leaves Facheiro's folder to it. `checksums.json` lists the release files under `files` and the git checkout's development files under `dev` (verified when present); it must match: regenerate it with `php build/make-checksums.php` in the same commit as any change to a tracked file, and keep `SelfCheckScanner::$dev_only` and the `export-ignore` lines of `.gitattributes` in step with `.distignore` (the build script refuses otherwise). Never add a skip list to the self-check: `.git`, `vendor/` and `node_modules/` are the only unlisted folders, and they are reported (PHP in `.git`, an unverified dependency folder), not ignored.
- **Sealed settings have one write path**: every change to `facheiro_false_positives`, `facheiro_signatures` or `facheiro_settings` goes through `Facheiro_Seal::update()` (lock, fresh read, save, seal only the entries that changed). A bare `update_option()` on them is indistinguishable from an attacker's and gets reported. `Facheiro_False_Positives::rules()` returns only sealed rules (and `reset_cache()` also drops the seal's per-process cache, which the abilities rely on in the long-lived MCP process); scans report the rest through `Context::$preflight`, which the self-check stage runs once per scan. Accepting a tampered state (`Facheiro_Seal::accept()`) is for administrators on the admin pages or WP-CLI only, never an ability.
- False positives get downgraded with an explanation (`Signatures::known_benign()`, hex-filename annotation), not silently suppressed — an attacker can hide behind any known-benign name. Administrator marks (`Facheiro_False_Positives`) keep the finding in the table (`fp` column: 0 none, 1 matched, 2 marked but the file changed) and in the JSON export; a mark on a file finding is bound to the file's SHA-256, and a mark on a DB finding to the SHA-256 of the scanned value (`value_sha256`, passed by the engine in the Reporter's `$meta` argument, which text and JSON ignore), and either stops applying when the content changes.
- **Nothing leaves the site on its own.** Samples are downloaded by the administrator (never uploaded), `wp-config*` is never packaged or read for an assistant, the VirusTotal link carries only the hash and is opened by the browser.
- **Recovery mode is inert without a key**: `recovery.php` answers 404 unless `<folder holding plugins>/facheiro-recovery-key.php` holds a valid, unexpired key (a SHA-256 created by the plugin or WP-CLI, or a hand-written key of at least 24 characters). The engine is loaded only after sign-in. Sessions are HMAC-signed cookies (HttpOnly, SameSite=Strict, one hour) keyed on the key, so replacing or revoking it ends them; every action needs a token bound to the session; only hand-written keys get the one-second delay and the per-client lockout (a lockout on generated keys would only let attackers block the owner, and a delay would let anyone tie up PHP workers while adding nothing against a 190-bit key). The state folder must be owned by the PHP user with no group/other access, steps never trust the stored options (they are rebuilt and passed through `scanall_context()`, so `dryrun` is forced and `restore` dropped), a unit started `MAX_ATTEMPTS` times stops the scan, and start/cancel take the job lock. Generated keys are returned once in the ajax response and never stored in plain text. It is report-only like the admin scan, reads `wp-config.php` with the engine's parser (never `include`), keeps its state in exit-guarded files in a private folder (system temp first), and escapes every output with `App::h()`. No ability or assistant tool can create a recovery key.
- **AI assistant surface** (`Facheiro_Abilities`): administrators only, no ability that cleans/restores/writes site files, every output with scanned data carries `untrusted_data_notice` (paths, details, context and file contents are attacker-controlled; the triage prompt says so). Each call drops the cached Facheiro options first because `wp mcp-adapter serve` is one long-lived process.
- The output contract (text format, JSON events, exit codes) is what `tests/regress.sh` protects: a change there is a deliberate decision, documented in the site reference (`site/referencia/`, `site/en/reference/`) in the same commit, not a side effect.

## Style

Procedural-flavoured PHP matching the existing files: `////` banner comments for sections, snake_case helpers, explicit `return (...)`, Yoda-ish comparisons (`false === $x`), errors suppressed with `@` only where the failure is handled on the next line. Formatting sniffs are intentionally not enforced; security/DB/WP sniffs are.
